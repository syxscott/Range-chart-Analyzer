## 1. 总评

**结论：当前版本未达到专业级科研软件标准，可在"研究助手"或"教学工具"层级使用；但存在若干 P0 缺陷阻碍其在正式科研发表中的可信度。**

主要问题集中在三类：(a) **合并算法的科学严谨性**——多运行合并会产生自然界不存在的嵌合共识行，威胁可复现性；(b) **数据丢失链**——prompt 要求的关键字段（端点性质、精确层号、命名人）在 Python/JS 两端均被丢弃；(c) **安全回归**——2026-07-19 已修复的 SSRF 重定向防护在 server.py 中被新的 pinning opener 覆盖。

## 2. 🔴 P0 严重与高危发现

### 2.1 【CONFIRMED×3，回归】SSRF 重定向防护已失效 — server.py:471
- **文件**：`server.py:96 → 471`、`rca_core/llm.py:1012`
- **机制**：server.py:96 先 `from rca_core.llm import ...`，触发 llm.py:1012 `install_opener(build_opener(_NoRedirect()))`；紧接着 server.py:471 `install_opener(_make_pinning_opener())` **覆盖了它**。新 opener 仅 build_opener(_PinnedHTTPSHandler())，无 _NoRedirect handler。
- **失败场景**：服务端发起 LLM 调用时若遇 302 Location: http://169.254.169.254/...，默认 HTTPRedirectHandler 自动跟随到云元数据端点或内网 IP，绕过 server.py 端点校验。
- **严重度**：🔴 P0（SSRF，可访问云元数据密钥 / 内网服务）
- **修复方向**：server.py:_make_pinning_opener() 末尾 `build_opener(_PinnedHTTPSHandler(), _NoRedirect())`；或显式合并两个 opener 的 handlers。

### 2.2 【CONFIRMED×7】Apply Edits 触碰已销毁表格整体崩溃 — gui_fluent.py
- **文件**：`gui_fluent.py:998-1008` 周围
- **机制**：`_table_widgets` 从不清理（未跟踪 widget→table 的反向引用）。Apply Edits 后表格被销毁但表对象仍被引用，二次写入时触发 RuntimeError。
- **失败场景**：用户在 Apply Edits 后立即再次点击 Apply Edits → 崩溃；当前捕获但丢失用户编辑内容。
- **严重度**：🟠 高（功能失效、用户数据丢失）
- **修复方向**：维护 `_table_widgets` 字典并在 setSourceModel 后/table 被替换时调用旧 widget 的 deleteLater()。

### 2.3 【CONFIRMED×10】多运行缓存预填假设连续命中 — server.py
- **文件**：`server.py:999-1007` + `1025`
- **机制**：prefill 循环把命中追加到 ok_datas，但判定"是否要重跑"用 `if run_idx < len(ok_datas): continue`，假设 ok_datas 与 slot 索引一一对应。非连续命中（如 slot 0 命中、slot 1 失败、slot 2 命中）→ 真正的 miss（slot 1）被跳过、已命中的 slot 2 被重跑并覆盖原缓存。
- **失败场景**：3 跑设置、第 1 跑 slot 1 失败 → 重试时仅跑 slot 2、覆盖 slot 2 的原缓存、slot 1 永远缺失。merge 收到 [d0, d2, d2'] 假装 3 跑完整。
- **严重度**：🟠 高（数据完整性 + 资源浪费 + 静默）
- **修复方向**：用 `slot_idx → cached_data` 字典而非有序列表，判定条件改为 `if slot_idx in cache_dict: continue`。

### 2.4 【CONFIRMED×6】columnar sections 被二次合并覆盖 — rca_core/aggregate.py

## 4. 古生物领域严谨性专章

作为古生物学家审阅，我必须强调**这套工具若用于正式科研发表，存在以下系统性问题**：

### 4.1 合并算法违反生物地层学的基本假设
**最严重问题**：rca_core/aggregate.py 的逐字段独立众数投票会产出**自然界不存在的嵌合共识行**。例如：3 跑全部以 (S,X) 为键，run1=(Bed 7, Bed 9, B Zone)、run2=(Bed 8, Bed 10, C Zone)、run3=(Bed 6, Bed 11, A Zone)——3 跑每个字段都完全不一致、没有任何 run 给出 (Bed 6, Bed 10, A Zone) 这个组合，但合并结果却返回它并报 agreement="3/3"。

在生物地层学中，**分类单元 + 生物带 + 层位的组合是地质学事实**，不是各自独立的可投票特征。一个分类单元的 FAD/LAD 与其所在的生物带有约束关系——侏罗纪早期 (Bed 6) 出现白垩纪菊石带 (A Zone) 在自然界不成立。当前算法违反这一基本约束。

**建议**：合并前在每个分组内做"完整行投票"或"先聚类再取代表性完整行"；引入 hard constraint 校验（如层位年龄必须与生物带一致）。

### 4.2 物种命名（学名/命名人）归一化有科学风险
rca_core/aggregate.py 的 ID 归一化（学名大小写/空格/命名人）**可能在分裂或错误合并不同分类单元**：
- 同名异物（homonym）：不同分类单元恰好同名
- 异名（synonym）：同一分类单元在不同文献用不同名字
- 命名人差异："Smith, 1950" vs "(Smith, 1950)" vs "Smith 1950" 是同一作者三种写法

当前归一化规则对小写/空格的"清洗"可能把三个不同分类单元错误合并为一行，也可能在异名情况下把同一分类单元拆为多行。**这是分类学数据的硬约束，必须做专家审核或显式 ICZN 规则库匹配**。

### 4.3 端点性质（endpoint_kind）丢失违反延限图数据模型
延限图（FAD/LAD）的关键学术价值在于区分：
- **observed FAD/LAD**：真实首现/末现，受采样密度影响
- **projected**：推断但未直接观察到
- **truncated**：因为图表截断而人为缩短

prompt.py 明确要求这三种区分，exporter 列定义也预留了空间（"endpoint_kind" 在 _KNOWN_SPECIES_KEYS），但 **Python 端和 JS 端均将其丢弃**。结果是：当前工具导出的延限数据**无法区分真实产出与推断产出**——审稿人无法评估数据质量。

### 4.4 菊石带/生物带归属与地层顺序约束未做交叉校验
prompt.py 列出"列分立"与"阶 vs 组/段"两条铁律，但**模型输出后没有 post-hoc validator** 校验：
- 同一地层剖面中"阿尔布阶"不应与"凡兰今阶"在上下颠倒的两行出现
- 一个分类单元的 range_base > range_top 时应报警（FAD<LAD 反置）
- section 字符串引用与 sections 数组中 name 应匹配

quality.py 仅做了 `range_top < range_base` 单点检测（quality.py:284-304），且是 scoring-only 不阻止数据流。需要**前置/后置的硬一致性校验器**。

### 4.5 导出保真度不足以支撑论文 supplementary
- other_fossils 字符串型化石名在 xlsx 中被丢（已发现）
- 多语言术语映射在日文有"組/段"误用问题（已发现）
- CSV 注入防护两端实现不完全一致（已发现）
- TSV→Excel 剪贴板路径暴露公式注入（已发现）

**这些缺陷意味着即使科学数据正确，导出过程会引入二次数据失真**。建议在 exporter 入口加 invariant 校验（如每个物种行必须有 species+section+range_base+range_top 四元组）。

### 4.6 总体专业级评级

**当前版本适合**：教学演示、个人研究助手、初步数据浏览。

**当前版本不适合**：(a) 论文 supplementary 数据生成；(b) 大规模地层数据库录入；(c) 多机构联合数据汇交；(d) 需要 PROV-O / 数据血缘的科研项目。

## 5. 做得好的点（证据化）

- **测试覆盖广**：50+ 测试文件覆盖核心/聚合/provider/服务器/GUI/前端，375 个 core 测试 + 43 个 frontend 测试 + 37 个 aggregate parity 测试（按 [memory] 中数据）。

- **i18n 兜底链**：JS 和 Python 都有"key → 内置回退 → 英文"的多层兜底。
- **PROMPT_VERSION 缓存键设计**：通过版本号避免新旧 prompt 结果混用缓存——但 ABUNDANCE/COLUMNAR 共享同一版本号是设计缺陷（已在 §3 列出）。
- **image enhancement 双路径**：Pillow stdlib-only + cv2 可选回退，兼容部署。
- **6 级 JSON 解析回退链**：从去 fence → 控制符 → 严格 parse → 平衡 {} → 平衡 [] → prose 嵌入，健壮性好。
