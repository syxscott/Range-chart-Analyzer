## 一、总体结论

**1. 三端都修过同一批真实事故，但「修一处、漏两处」的模式已经固化成本项目的结构性成本。**
最典型的证据是 `_collect_extraction_futures`：Fluent 版加了 `should_cancel` 取消能力并把返回值
从 `list` 改成 `(results, cancelled)`，**Tkinter 端仍是旧签名**（`gui.py:123` / `gui.py:1953`）。
GUI 审查把它列为「本项目结构性风险的教科书案例」——主审复核属实。

**2. 你担心的「GUI 体量」比预想更严重，但形态和你想的可能不同。**
不是「文件太长」，而是**单类太长 + 注释是变更日志**：

- `gui_fluent.py` 4219 行，但真正的上帝单位是**类**：`ExtractPage` 一个类 **2064 行、56 个方法**（L945–3008）
- 文件里 **964 行纯注释（22.8%）**，其中 **104 行**带 `REVIEW-`/`AUDIT-`/`FIX-`/`Bug-` 前缀，
  记录的是「这个 bug 曾经是什么」——**属于 git history 的内容**
- 主审实测：`__init__` 单个构造函数 **343 行、108 个顶层表达式调用**，一次性构建整个主窗口

**3. 唯一 P0 是必崩的，但触发路径很窄。**
`gui_fluent_providers.py:756/770` 用了 `self._tr`，而 `__init__` 只赋了 `self._t`。
用户新建/编辑 provider 时**留空名称或端点点保存** → `AttributeError` → Qt 槽中断。

**4. 有一类缺陷三份报告都没覆盖，是主审独立实测出来的：无结果时导出静默失败。**
Tkinter 的「导出全部 JSON」按钮**恒为 `state=normal`**，handler 无结果时 `return`，
**不弹窗、不改状态栏**——用户点了完全没反应。Web 端有 `toast`，Fluent 端会灰化按钮，只有 Tk 两样都没有。

**5. 健壮性整体优于预期——三个猜测性高发区全部落空。**
死按钮（AST 扫描 GUI 全端 0 个未接线控件）、XSS（`rcaEsc()` 11 条注入用例实测全转义）、
竞态（连点 Extract / 提取中取消 / 切语言 / 切主题全部有正确不变量保护）。这部分做得扎实。

## 二、P0（1 条）

### F-01 Fluent provider 向导保存路径必崩

- **位置**：`gui_fluent_providers.py:756`、`:770`；构造函数 `:511`
- **主审已独立复现**：

```
ProviderWizard.__init__  → self._t = translate        # 只赋了 _t
第 756 行                 → self._tr.t("wizard.fillRequired")        ← _tr 不存在
第 770 行                 → self._tr.t("wizard.extraHeadersIgnored", {"reason": ...})
```

三处错误叠加：属性名错（`_tr` vs `_t`）、调用形式错（`.t()` vs 其它处的 `_t(key).format(...)`）。
调用方 `gui_fluent_providers.py:1052/1084` 传的 `translate` 是可调用对象 `self._t`。

- **复现**：GUI → 提供商页 → 新增/编辑 → 名称或端点留空 → 保存 → `AttributeError`；
  或填入非法 `extra_headers` → 保存 → 同样崩。Qt 槽抛异常会中断该槽，**向导卡在无法保存状态**。
- **修法**：`self._tr.t(k)` → `self._t(k)`；第二处的 dict 参数按现有风格改 `.format(reason=...)`。

### 主审实测推翻了一条成员判断

**F-10 原文**：「UI 线程阻塞数百毫秒到数秒，用户会以为程序卡死」——**这是读代码推测，不成立**。

主审用真实 `RangeChartApp` 驱动 `_on_result()` 实测：

| 行数 | 耗时 | 每行 |
|---|---|---|
| 200 | 0.358 s | 1791 µs |
| 800 | 0.093 s | 116 µs |
| 2000 | 0.114 s | 57 µs |
| 5000 | **0.117 s** | 23 µs |

**耗时在 200 行之后基本持平**，不是线性增长（ttk.Treeview 行插入是 C 侧批处理）。
第一次 200 行的 0.358 s 是 **ttk 样式首次初始化**的一次性开销。
**已把 F-10 从 P2 降级为 P3**，并在该报告内注明原判断属推测。

### F-14 高 DPI：主审把「无法验证」变成实测

GUI 报告标为「无法在本环境实测」。主审补测了 DPI 感知状态：

```
GetThreadDpiAwarenessContext = 24592      # 应用自身从未调用 SetProcessDpiAwarenessContext
GetDpiForWindow             = 96
tk scaling                  = 1.3339898  ← 不是代码设的，是 Tcl 在 UNAWARE 下自己算的
```

结论**不是「界面已错乱」**（当前机器 100% 缩放，看不出问题），
而是**「没有任何一层声明过 DPI 策略，Tcl 在替我们猜」**。换 125% 缩放或双屏异缩放时 Tk 会错位。

## 九、本次审查的限制

1. **PySide6 与 qfluentwidgets 未安装**，Fluent GUI 的所有结论均来自**静态分析**（AST + 读码），
   无法实测渲染、主题、信号时序。F-01 是主审用 AST 确认属性未赋值 + 读调用方确认的，
   置信度高但**未在真实 Qt 进程里跑过**。
2. **Web 端未在真实浏览器里操作**，DOM 行为靠测试 harness（stub 的 `classList` 与真 DOM 有差异）。
3. **Tkinter 实测在 `root.withdraw()` 下进行**——无显示器绘制，Treeview 逐行插入的开销是真实的，
   但控件实际绘制、焦点、剪贴板交互未覆盖。
4. **WEB-04 / WEB-05 的证据边界**（审查者主动标注，主审采信并据此收严了主报告的表述）：
   - WEB-04 只测到 `rcaRenderResults` 的**字符串拼接**（36 ms / 5000 行）；
     1.62 MB HTML 塞进 `innerHTML` 之后的解析/样式计算/布局/绘制成本
     **必须在真实浏览器用 DevTools Performance 面板实测**，本轮未做。
   - WEB-05 的**比值是硬事实**（脚本从 CSS 源解析），受影响选择器已逐一确认；
     但 WCAG 1.4.11 只约束「理解内容所必需」的非文本元素，三个受影响元素分别落在：
     开关轨道（状态靠滑块位置传达 → **整改必要性中等**）、置信度环 stroke
     （环内还有百分比数字，颜色是冗余编码 → **低**）、卡片边框
     （**需设计确认**是否为纯装饰）。**不应直接按「失败」处理。**
